## 名册镜像（写入时必须同步）

名册在模块里共有 5 份，起点分别是 R1 `base+0x11A7D10`（主名册）、R2 `base+0x2C82198`、R3 `base+0x2C8BE88`、R4 `base+0x2C95B6C`、R5 `base+0x2E80968`，槽位间距都是 0x258。

- R1 是当前状态：游戏学技能扣 JP 时只改 R1
- **R2、R5 是镜像，界面刷新时会把 JP 写回 R1**：只改 R1 的 JP，刷新后会被冲回旧值。写 JP 时三份要同时写，2026-10-16 已验证（齐克 JP 写成 999 后，学 300 JP 的技能变成 699）
- Brave 只写 R1 时，游戏会自己同步到 R2、R5；JP 不会。原因还不清楚，修改器统一对 R1、R2、R5 三份同时写
- R3、R4 以及堆上的拷贝是旧快照，不跟着变，不要写

## JP 与职业等级（2026-10-16 实测）

- 游戏界面显示的 Job Lv 是按 **累计 JP（J-EXP，+0xAE）** 和门槛 200/400/700/1100/1600/2200/3000 算的
- 新职业能不能解锁，看的是 **+0x74 起的职业等级字段**：每字节 2 个职业，**高 4 位 = 偶数号职业，低 4 位 = 奇数号职业**（写入 0x12 后，游戏进职业界面会按 J-EXP 自己重算成 0x21：见习战士 274→Lv2 在高位，道具士 116→Lv1 在低位。早先「0x13 让骑士解锁」被误读成低位是见习战士，已更正）。游戏会按 J-EXP 自动重算这个字节，所以写错只是暂时的
- +0x2F 的 3 字节位图不影响解锁，不用写
- 正确的「获得 N JP」：当前 JP += N，累计 JP += N，职业等级字段按累计 JP 重新算（只升不降），R1/R2/R5 三份同时写；写之前**玩家要退到世界地图或队员列表**，否则游戏会拿选中队员的工作副本写回。实测：齐克见习战士 +100 → Job Lv2、J-EXP 274、NEXT 126、JP 799，能正常转职
- **已学技能**（+0x32 起每职业 3 字节）：只写名册三份不生效，界面读的是选中队员的工作副本（模块内另有紧凑格式拷贝：module+0x1876C8B / +0x374189B / +0x3749D1B，学技能位图偏移在拷贝里 −0x4F 处，JP 在 +0x4F）。决定**不改已学技能**，让玩家在游戏里用 JP 正常学
- 化学士在游戏里叫「道具士」

## 战斗单位（2026-10-17 实战确认）

- 数组：第 i 槽 = `base+0x1853CE0 + i*0x200`，i = 0..22。界面读的就是这一份：只改这里，战略视角里敌人 HP 立即变了。`base+0x898xxx` 和堆上的拷贝是下游，不要写
- 第一关里 i=0 迪利塔（客座）、i=1 阿加斯（护卫目标），2..7 敌人，16..19 我方；槽 20 的 `+0x01` = 0xFF，是无效拷贝
- `+0x00` 角色码 · `+0x01` 上场标记（0xFF = 空槽 / 无效） · `+0x02` 名册序号（我方 0..49；客座不是，迪利塔 0x32、阿加斯 0xFF） · `+0x03` 职业 · `+0x04` 调色板（**不是阵营**，敌人可能是 1 也可能是 3） · `+0x05` 队伍与操控（0x30 位 = 队伍，0 = 蓝方、1 = 敌方、2/3 未见过；0x08 = 玩家操控；样本：我方 08/0B、GUEST 04、敌人 94/90/D0/10） · `+0x06` 性别（0x80 男 / 0x40 女） · `+0x28` EXP · `+0x29` 等级 · `+0x2A/+0x2B` 战斗中 / 原始 Brave · `+0x2C/+0x2D` 战斗中 / 原始 Faith · `+0x30/+0x32` 当前 / 最大 HP · `+0x34/+0x36` 当前 / 最大 MP · `+0x41` CT（用迪利塔 22、阿加斯 2 核对过；当前行动单位界面上显示 100，内存可能已经是 2） · `+0x61` bit 0x20 = 倒下 · `+0x1FC` 名字编号
- 分类：我方 = 队伍 0 且名册序号 < 50；友军 = 队伍 0 的其余单位；敌方 = 队伍 1；队伍 2/3 没见过，一律不碰
- 2026-10-17 雪地剧情战踩坑：旧版按 `+0x04 == 3` 认敌人，这一关敌人调色板全是 1，一个都没认出来，「双方都有活着的单位」不成立，被判成未在战斗中
- 我方锁血实测：打开后，被魅惑的队员攻击自己人、自己人反击、3 个敌人围攻拉姆萨，我方都没掉血
- 阵亡倒计时（3 颗心）的字段还没找到：唯一等于 3 的字节是槽位号。要等倒计时从 3 变成 2 时做内存对比

## 「战斗中」标志（候选，2026-10-17）

战斗结束后战斗数组不会清空（胜利后敌人全倒，数据原样留着），所以「数组里有单位」不能当作战斗中。目前修改器的权宜做法是：双方都还有活着的单位才算战斗中。

用 3 张模块快照来筛：战前世界地图（`mod-worldmap-after-battle1.bin`）、野外战斗中（`mod-battle2.bin`）、战后世界地图（`mod-after-battle2.bin`）。条件是「两张世界地图值相同、战斗中不同、且都是 0/1」，剩下 16,947 处，大多是界面状态。战斗数组附近只剩 3 处，都是「世界地图 0、战斗中 1」：

- `base+0x184FBD0`
- `base+0x18513D0`
- `base+0x1853C08`（就在数组起点前 0xD8 字节，最可疑）

**`base+0x1853C08` 只是「遭遇战（野外随机战）」的战斗中标志**：2026-10-17 在一场剧情战（有迪利塔、阿加斯两个 GUEST）里读到的是 0，另两个候选也是 0。修改器改为「遭遇战标志为 1，或者双方都有活着的单位」。剧情战的标志还要另找。以下是遭遇战里的验证记录：（另两个候选在战斗中仍是 0，已排除）。逐秒监视一场野外战斗的结果：03:23:39 剩 1 个敌人，值为 1；03:23:54 最后一个敌人倒下，仍是 1；03:24:10 战斗场景结束，变回 0；回到大地图后保持 0。修改器已改为按这个标志判断战斗中，标志为 0 时不读战斗数组。

## JP / 经验倍率（2026-10-17 实战验证）

- 做法是按差额补发：每 200ms 对比我方单位的累计 JP（战斗槽 `+0x11E`）和 EXP（`+0x28`），游戏每发一次 d，修改器就再补 (倍率−1)×d；EXP 最多补到 99，升级仍由游戏自己处理
- 实测（JP 5×、经验 2×）：齐克攻击一次，游戏发了 JP 26、EXP 11，实际涨了 JP +130、EXP +22。同场其他 4 人的同职业「分享 JP」游戏原本发 5，也被放大成 +25
- 战后写回：战斗结束、回到大地图后，5 名出战队员名册里的当前 JP、累计 JP、职业等级、EXP、等级，与战斗结束时的战斗槽逐项一致（0 处差异）。三人在战斗中升级，由游戏自己完成
- 战斗槽 → 名册的对应关系：战斗槽 `+0x02` = 名册序号；战斗槽 `+0xE4` / `+0xF0` / `+0x11E` 分别对应名册 `+0x74` / `+0x80` / `+0xAE`

## 回合标记：总能移动 / 总能行动（2026-10-17 剧情战实测）

- 战斗槽 `+0x1B8` = 当前正在行动的单位（1 = 是）
- `+0x1B9` 本回合状态位：回合开始时为 0，移动后置 bit0（0x01），行动后置 bit1（0x02）
- `+0x1BA` 行动后变成 1
- 总能移动：移动后清掉 bit0，「重新移动」就会从当前位置接着走（不清时是撤销、回到出发点）
- 总能行动：游戏在行动结算之后很快就决定「回到指令菜单」还是「选择面向」。200ms 轮询会错过动画短的普通攻击，改成约 10ms 的高频循环（只读当前行动单位的这 3 个字节）之后稳定：攻击未击杀 1 次、击杀 2 次，每次都回到了指令菜单
- 移动 + 行动都用完、已经进入选面向之后再清标记无效（此时 `+0x1B8` 已是 0）
- 需要咏唱的魔法（黑魔法等）选完、定好方向就结束回合，不受这两个开关影响

## 剧情战结束后（2026-10-17）

结算之后进入剧情过场：遭遇战标志 = 0；战斗数组被过场重新利用（活着的我方 0 个、活着的「敌方」1 个，应该是演出角色）。「双方都有活着的单位」这一条不成立，修改器判定为不在战斗中，持续开关自动关闭，不会写过场里的单位。

## 移动力 / 跳跃力、咏唱（2026-10-17 剧情战实测）

- 战斗槽 `+0x42` 移动力、`+0x43` 跳跃力（u8）：敌方骑士 3/3、弓箭手 3/3、格斗家 3/4，拉姆萨（格斗家 + 战靴）4/4，与原版一致。把拉姆萨的 `+0x42` 写成 8 后，可移动范围几乎覆盖整张地图
- 咏唱：选了需要咏唱的魔法后，`+0x61` 置 0x08（咏唱中），`+0x18D` 从 0xFF 变成剩余咏唱时间（冰结 = 4）。每过一个时间单位减 1（实测 CT 涨了 12、速度 4，倒计时 4→1），归零时法术放出，`+0x18D` 变回 0xFF、`+0x61` 的 0x08 清除、扣 MP
- 「总能行动」开着时，选完咏唱魔法也不会进入选面向（已经清掉了行动标记），回合要手动「待命」才结束；之后因为游戏认为本回合没行动过，会多给剩余 CT（霍特曼待命后 CT = 42）
- 咏唱即发实测：把 `+0x18D` 写成 1 后，法术在时间轴下一格就第一个结算（时间轴上紧接着显示「闪雷」），排在所有单位行动之前。FFT 的咏唱法术本来就不会在施法者自己的回合内结算，要「当场放出」只能改游戏代码。没有试写 0：游戏可能把 0 当特殊值
- 推荐组合：锁定我方 CT + 咏唱即发 + 总能行动，可以连续施法

## 总能行动在升级时失效（2026-10-17 已修）

现象：两次击杀敌人时被判定为已行动，当时角色都升级了。原因是战斗单位身份（BattleIdentity）包含等级：击杀当场升级，高频清除的身份校验不通过而跳过，等 200ms 主循环刷新缓存时，游戏已经进入选面向。修法是身份只保留战斗中不变的字段（槽位标记、阵营、角色码、职业、名册序号、名字编号）；JP / 经验倍率原本靠身份变化识别升级帧，改成单独比较等级。
